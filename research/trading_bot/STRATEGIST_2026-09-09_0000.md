## 2. Why nothing told us — three green proxies, one lost day

### 2a. The T30 ledger summary says `days_attempted 15 / days_clean 15` = **1.00**

This is the T31 denominator defect (found blind 24h ago, `STRATEGIST_2026-09-08_0000.md` §2)
**realised in production, on a different instrument**. `record()` only runs inside a collector
run, so a day on which cron never fires gets no ledger entry at all: not failed, *nothing*.
The denominator did not grow. The ratio is a perfect 1.00 on a day we lost.

The 09-08 00:00 note's scope call — *"T30 is NOT exposed"* — was right about the **gate** and
should not be read as right about the **ledger**. T30's gate (`t30_borrow_evaluate.py:309`,
`len(clean_days(ledger)) < MIN_CLEAN_DAYS`, `MIN_CLEAN_DAYS = 30`) counts clean days absolutely,
so an outage can only **delay** it, never fake it. That still holds and is still the safer gate
design. But T30's ledger *summary line* has exactly the T31 blind spot, and it is the line a
human reads.

### 2b. The T52 input-recency alarm printed `OK   T30_BORROW   22.03h / 48.0h` — for a feed that missed a day

This is the more serious finding, because T52 is the monitor we built *precisely* so a proxy
could not lie to us. On a `daykeys` instrument it lies in two stacking ways
(`scripts/trading_bot/input_recency_alarm.py`):

1. **A bare date key is credited to the END of its day.** Newest key `2026-09-07`, now
   `09-08T22:00Z`, reported age **22.03h**. The true elapsed time since the last *collection*
   is ~46h. Every `daykeys` instrument is reported **24h younger than it is**.
2. **`allowed_hours = cadence_hours * tolerance = 24 * 2.0 = 48`** (line 217). A 24h feed is
   allowed to be 48h stale before it is called.

Stacked, a calendar-daily instrument must miss **two consecutive collections** before T52 says
STALE. One lost day is structurally invisible to the alarm — and one lost day is exactly what
happened.

3. **A third, T30-specific error:** T30 is registered `business_days=True` (line 179–180), which
   subtracts weekend hours from the age. But the T30 collector is **calendar**-daily — its own
   ledger contains clean entries for 08-29, 08-30, 09-05 and 09-06, all weekend days. The
   weekend grace is therefore not a grace, it is a suppression: a Friday-evening→Monday outage
   could stay green on top of the 24h + 48h already above.

### 2c. The supervisor's own absences leave no trace at all

Ticks h12/h15/h18 produced **no files whatsoever** — no canary nonce, no `input_recency_*.txt`,
no `claude_*.log`. Those artifacts are written by `durable_tick.sh` *before* Claude starts, and
the auto-stamp that writes "this tick wrote no FINDINGS line" is written by the same script. So
a tick that never runs cannot record that it never ran. `research/FINDINGS.md` shows an unbroken
sequence of dated entries across 09-08 with a nine-hour hole in it and no marker in the hole.

Same failure shape as T52's founding case, one level up: **we monitor the instruments, and
nothing monitors the monitor's own attendance.**

**Date correction (an estimate moving, NOT a frozen rule moving).** The frozen T30 rule is
"30 clean days", full stop; `~09-22` was only ever our arithmetic about when that would land.
With 15 clean days banked (08-24…09-07) and 09-08 lost, 15 more clean days run 09-09…09-23, so
the 30th clean day is recorded **2026-09-23 16:30 CEST**, readable that evening. The T30 fork
is **~09-23, not ~09-22**, and it now falls on the same day as T31's collector gate. Every
further host outage moves it another day, one-for-one.

**The one thing worth building next (T72).** A strictly additive, read-only **calendar-gap
reader**, on the same pattern the 09-08 tick chose for T31: do not patch a running monitor's
semantics blind, add a companion that computes the honest number. For every `daykeys`
instrument it enumerates calendar (or trading, per that instrument's declared cadence) dates
from day 0 to today and reports **which dates have no ledger entry at all** — the quantity that
neither the ledger summary nor T52 can express. Expected output today: T30 missing `2026-09-08`;
T31, T33, T45 complete. It also fixes the three specific alarm errors in §2b **in the companion,
not in the live alarm**. Filed priority 1 for the next CHUNK B tick.

**Second (T73).** A missing-tick reconciler: the first tick that runs after a gap enumerates the
expected 3-hourly slots since the previous log artifact and stamps each absent one into
FINDINGS. Cheap, and it is the only way an unattended programme can tell "nothing happened"
from "nothing was recorded".
