## 2. THE FINDING — T31's 09-23 gate is a scheduled FAKE-PASS (denominator defect)

The T31 protocol, frozen 2026-08-24 before any snapshot existed
(`research/trading_bot/T31_DERIBIT_FORWARD.md`, §"Frozen decision rules", item 1), specifies:

> `ledger.summary.days_clean / days_attempted ≥ 0.95` (with `days_attempted` = **calendar days
> since day 0, so silent cron death counts as failure**)

The implementation does not do that. `scripts/trading_bot/t31_deribit_collect.py:219`:

```python
ledger["summary"] = {
    "days_attempted": len(days),          # days = ledger["days"], i.e. days the script RAN
    "days_clean":  sum(1 for d in days.values() if d["status"] == "clean"),
```

`record()` is only ever called from inside a collector run. A date on which cron never fires —
the machine is down, the crontab line is lost, the process dies before `record()` — **never gets
a ledger entry at all**. It is not counted as failed; it is counted as nothing. The denominator
does not grow, `days_clean / days_attempted` stays exactly `1.00`, and on 2026-09-23 the gate
returns a clean PASS on a collector that may have been dead for a week.

This is the **T52 failure shape exactly**: a green proxy that cannot represent its own absence.
T52 was born because a live process, a rendering dashboard and an intact hash chain all stayed
green through a 56-hour MEME ARENA input outage. The T31 ledger has the same blind spot, on a
gate that fires in 15 days.

**Severity: it has not bitten yet.** The enumeration in §1 proves T31's ledger currently has an
entry for every one of the 15 calendar days since day 0, so the true calendar-denominator ratio
today is also 15/15 = 1.00. The defect is not a corrupted past reading; it is a **live exposure
for the next 15 days**, and it is asymmetric in exactly the wrong direction — it can only turn a
dead collector into a PASS, never a live one into a fail.

**Scope.** T30 is **NOT** exposed: its gate is an absolute count of 30 CLEAN days
(`t30_borrow_evaluate.py:309`, `MIN_CLEAN_DAYS = 30`), so an outage can only *delay* the gate,
never fake it. This is the safer gate design and it should be the default. T33 uses
`len(trading)` as its denominator (`t33_us_options_collect.py:296`) and is therefore
**structurally exposed in the same way** ahead of its ~10-07 gate, with the extra wrinkle that
its denominator is a trading-day calendar; that audit is deferred to a CHUNK B tick as T67's
second half, and is explicitly not asserted clean here.

**Response, and why it is not a rule change.** The frozen protocol text already says
*calendar days since day 0*. The code deviates from the text; the text is authoritative and the
code is wrong. So the disciplined move is **not** to edit the frozen rule and **not** to patch
the live collector's ledger writer 15 days before its gate (rewriting a running instrument's
bookkeeping semantics is how this programme has reset its own clocks ten times on BASKET1).
The move is a **strictly additive, read-only companion gate reader**, pre-registered and pinned
now while the answer is still blind, that computes the ratio the frozen text specifies:

```
days_attempted := (gate_date - day0).days + 1        # calendar, not len(ledger["days"])
days_clean     := ledger entries with status == "clean"
PASS iff days_clean / days_attempted >= 0.95
```

Opened as **T67** (prio 1). It must be built and pinned at a CHUNK B tick **before** 09-23, and
run alongside — not instead of — whatever the collector's own `--status` prints. Where the two
disagree, the calendar reading is the verdict, per the frozen text. This is the same pattern as
T62 (T30 cluster diagnostic) and T63 (convexity cluster diagnostic): the frozen artifact is left
pin-clean and a blind companion is added beside it.
